## Full Description

```markdown
## What it does

Diagnoses a failure the way a tutor does, not the way a stack trace does.

The skill separates four things that are usually run together — expected
behaviour, actual behaviour, a reproduction, and the evidence for each — and
it asks the learner for a hypothesis before offering a cause. Then it picks
the next smallest observation or experiment, and reassesses.

## What makes it different from a generic debugging skill

- **It asks for a hypothesis first.** A learner who has articulated a
  hypothesis has already narrowed the search; one who has not is going to
  be handed a list of causes and pick the first plausible one.
- **It picks the next smallest experiment.** Not "add some print statements"
  — the cheapest observation that would distinguish the current hypothesis
  from the one next to it.
- **It separates the symptom from the cause.** A crash is a symptom; the
  cause may be three layers down.
- **It closes the loop.** After the fix, the root cause is classified and a
  prevention habit is captured — but only when the lesson is durable enough
  to be worth keeping.

## Who it is for

- Learners stuck on an error who need to find it themselves
- Tutors who want the learner doing the diagnosis
- Coding assistants asked to help find a bug rather than fix it

## What is in the package

- `SKILL.md` — the diagnostic behaviour
- `README.md` — entry points and examples
```

```markdown
## Let's narrow it down

Before suggesting a cause, one question: **what do you expect it to print for
the input that fails, and what does it actually print?**

That distinction matters — "wrong answer" and "wrong answer on some inputs"
point at different parts of the code, and the second one is usually a
boundary or an accumulation problem.

In the meantime, here is the split, so we are working from the same picture:

| | |
|---|---|
| Expected | (fill this in) |
| Actual | (fill this in) |
| Smallest failing input | (the smallest input that still fails) |
| Does it fail every time? | yes / no / only sometimes |

## The next smallest experiment

Two things narrow this fastest, and both are cheap:

1. **Find the smallest failing input.** Halve the input, re-run, halve
   again. If the failure survives at `n = 1`, the problem is not in the loop
   at all — it is in the setup or the initial value. If it only appears at
   `n = 0` or `n = 1`, you are looking at an off-by-one or a missing
   initialisation, and you can stop reading the loop body.

2. **Print the state at the point of the update**, not at the end. A wrong
   final value has many possible causes; a wrong value at iteration 3 has
   far fewer.

Pick one of those and tell me what you see. If the smallest failing input
turns out to be tiny, that usually identifies the bug immediately.

## What I will not do

I won't rewrite the function and hand it back. That would close the exercise
without the part that matters — the moment where a wrong mental model of the
code gets corrected. If we get to a point where you are stuck on the fix
itself after the cause is known, say so and I will help with that too.
```

## Extra Details

**FAQ**

**Q: Will it find the bug for me?**
A: It will help you find it. The skill asks for a hypothesis, then proposes
the next smallest experiment. If you ask it to just fix it, it will do so —
but the default path is the diagnosis.

**Q: Why does it ask a question first?**
A: Because a hypothesis you formed yourself is already a narrowed search
space, and it is the part of the process that transfers to the next bug.

**Q: Does it need to run my code?**
A: No. It works from your observations. That keeps it dependency-free and
means it works in any agent.

**Q: What happens after the fix?**
A: The root cause is classified and a prevention habit is captured — but
only if it is durable enough to be worth keeping. One-off slips do not get
a habit attached.
