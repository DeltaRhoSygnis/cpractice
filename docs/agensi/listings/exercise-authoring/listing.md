## Full Description

```markdown
## The problem

An exercise is only as good as its tests. A problem with vague tests produces
learners who fail for reasons they cannot see. A problem with no hidden tests
produces learners who pass by pattern-matching the public example. And the
failure is invisible: the exercise looks fine, the reference solution passes,
and the students still learn the wrong thing.

## What this skill does

- **Blueprint first.** Concept, objective, prerequisites, difficulty against a
  stated rubric, target solve time. The statement is derived from the
  blueprint — never written first.
- **A statement that stands alone.** Task, exact input format, exact output
  format, numeric constraints, one worked example, and any constraint on the
  solution (no recursion, no floating point, required complexity). Every
  ambiguity left in the text is a fairness complaint later.
- **A deliberate edge-case catalogue.** Nominal, minimal, maximal, boundary
  (both sides of every threshold), degenerate shape, negative and special
  values, input-format stress, idempotence, multi-case handling. Each test
  records the reason it exists.
- **Validation that actually runs.** The reference solution must pass every
  test. Deliberately broken variants — the mutants — must fail. The reference
  must be deterministic across repeated runs. Statement and tests must agree
  in both directions.
- **Difficulty you can check.** Cold timed solve, observation of where a
  learner at the intended level stalls, and a check that a common wrong
  approach is actually caught by a test.
- **Misconception mapping.** The two or three wrong beliefs a learner brings
  in, the error each produces, and the test that catches it. An exercise where
  a common misconception leads to a passing submission is teaching the
  misconception.
- **A three-level hint ladder.** Direction, approach, near-solution. Requested,
  never pushed. No level repeated. No hint may contain a hidden expected
  output.

## Why this beats prompting it yourself

A model will write you a plausible problem with three nice test cases. The
part that makes an exercise trustworthy — the mutant that must fail, the
boundary pair either side of a threshold, the check that the statement and
the tests agree — is the part that gets skipped, and it is exactly the part
that decides whether a judge is teaching or just grading.

## Output format

Nine fixed sections: blueprint, statement, metadata, reference solution, test
set, coverage table, misconception map, hint ladder, validation report. The
validation report is mandatory — a skill that writes problems without proving
they work has produced a liability, not an exercise.

## What is in the package

- `SKILL.md` — the authoring workflow
- `references/edge-case-catalogue.md` — the category catalogue, a coverage
  table format, and a mutation cross-check
- `README.md` — who it is for, entry points

## Who it is for

- Teachers and course authors writing practice problems
- Anyone whose problem set has known-bad tests
- Platform teams who need exercises a judge can grade fairly

## Summary

Below is a complete exercise package: statement, metadata, reference
solution, eight tests, a coverage table, a misconception map, three hint
levels, and a validation report. Two things to note — the boundary tests come
in pairs around the length limit, and there is a mutant for each, because a
test that catches no bug is not a test.

## 1. Blueprint

- **Concept:** single-pass maximum over an array
- **Objective:** choose a correct loop bound and initialise correctly
- **Prerequisites:** arrays, `for` loops, comparison operators
- **Difficulty:** single concept, non-obvious edge cases (level 2 of 4)
- **Target solve time:** 10–15 minutes

## 2. Statement

> Read a sequence of integers and print the largest one.
>
> **Input.** The first line contains an integer `n` (1 ≤ n ≤ 1000). The
> second line contains `n` integers, each between −10⁶ and 10⁶.
>
> **Output.** Print one integer: the largest of the `n` values.
>
> **Example.**
> ```
> 5
> 3 9 2 9 -4
> ```
> ```
> 9
> ```
>
> **Constraints.** The sequence always contains at least one value. You may
> not use a built-in maximum function.

## 3. Metadata

| Field | Value |
|---|---|
| Concepts | arrays, loop bounds, initialisation |
| Difficulty | level 2 of 4 |
| Duration | 10–15 min |
| Comparison mode | `exact_normalized` (all tests) |
| Visibility | 2 public, 6 hidden |

## 4. Reference solution

```c
#include <stdio.h>
int main(void) {
    int n, value, max;
    if (scanf("%d", &n) != 1) return 1;
    if (scanf("%d", &max) != 1) return 1;
    for (int i = 1; i < n; i++) {
        if (scanf("%d", &value) != 1) return 1;
        if (value > max) max = value;
    }
    printf("%d\n", max);
    return 0;
}
```

## 5. Test set

| id | name | vis | category | input | expected | why it exists |
|---|---|---|---|---|---|---|
| t1 | nominal | public | nominal | `3\n1 2 3\n` | `3` | baseline sanity |
| t2 | all-negative | public | negative | `3\n-5 -2 -9\n` | `-2` | catches a zero-initialised max |
| t3 | single | hidden | minimal | `1\n7\n` | `7` | off-by-one on the loop bound |
| t4 | max-length | hidden | maximal | `1000` values at 10⁶ | `1000000` | accumulator range |
| t5 | at-limit-lower | hidden | boundary | `1\n-1000000\n` | `-1000000` | lowest legal value |
| t6 | at-limit-upper | hidden | boundary | `1\n1000000\n` | `1000000` | highest legal value |
| t7 | duplicates | hidden | degenerate | `4\n5 5 5 5\n` | `5` | duplicate handling |
| t8 | descending | hidden | degenerate | `4\n9 7 2 1\n` | `9` | assumes unsorted input |

## 6. Coverage table

| Constraint | Test | Mutant | Must fail |
|---|---|---|---|
| `n ≥ 1` | t3 | drop the single-element path | t3 |
| `n ≤ 1000` | t4 | `n` inclusive→exclusive | t4 |
| values in range | t5, t6 | `<` → `<=` on max init | t5 |
| unsorted input | t8 | only compare with the first element | t8 |

## 7. Misconception map

| Misconception | Error it produces | Caught by |
|---|---|---|
| max starts at 0 | negative-only inputs print 0 | t2 |
| loop runs `i <= n` | reads past the end, garbage value | t3, t4 |
| input is sorted | only checks the first value | t8 |

## 8. Hint ladder

1. **Direction.** — Which value must your loop carry between iterations, and
   what must it hold before the first one?
2. **Approach.** — Read the first value into a variable, then walk the rest
   and update that variable when a later value is larger.
3. **Near-solution.** — The comparison inside the loop is
   `if (value > max) max = value;`. The initialisation before the loop is
   the part most solutions get wrong.

## 9. Validation report

- Reference solution passes all 8 tests — **yes**
- Mutants written: 4. Caught: 4. Survivors: **0**
- Reference deterministic across 3 runs — **yes**
- Statement/test agreement — **yes** (every constraint in the statement has a
  row above; every test's input respects the stated format)
- Categories considered and skipped: multi-case handling (the format is
  single-case by statement); idempotence (no accumulation across cases)

## Next steps

- Run the four mutants yourself before you trust this — they are the part
  that proves the tests work
- Add a case with `n` on its own line and values across two lines if your
  judge feeds input line-by-line rather than as a stream
- Swap the statement's example for one of your own so the public test is not
  memorisable

## Extra Details

**FAQ**

**Q: Will it write the tests for me?**
A: It designs them, with the category and the reason each one exists. You
still run them against your reference solution and your mutants — that
validation step is the point of the skill, and it is why the output format
requires a validation report.

**Q: What if my platform has its own problem format?**
A: Map the fields. The skill's test case has an id, a name, a visibility, an
input, an expected output, a comparison mode, and a rationale tag — that maps
onto most schemas directly.

**Q: Does it handle languages other than C?**
A: Yes. The C reference solution in the demo is an example; the method is
language-agnostic.

**Q: Isn't this just "write a programming problem"?**
A: The difference is the validation. A generated problem with three test
cases is a liability if a learner fails for a reason they cannot see. This
skill produces the mutation set, the boundary pairs, and the coverage table
that make the exercise trustworthy.

**Q: Can I use it to improve exercises I already have?**
A: Yes — ask it to audit a test set. It reports the missing categories, the
constraints left untested, and the mutants that would currently survive.
