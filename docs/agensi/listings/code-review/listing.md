## Full Description

```markdown
## What it does

Reviews code the way a good teacher reviews a student's program, not the way
a linter reports.

Findings are ordered by correctness and security first, then design,
maintainability, performance, and style. Each finding carries a severity
label and an explanation of the impact — what breaks, and when.

## What makes it different from a generic code review

- **It asks before it rewrites.** A discovery question first, because the
  intent behind a piece of code is often the thing that decides whether the
  finding is real.
- **It separates defects from preferences.** "This will lose data" and "I
  would have named this differently" are not the same category, and mixing
  them is why code review often feels like noise.
- **It requires verification.** A finding is not established until it is
  checked against a test or a concrete observation.
- **It teaches while it reviews.** The learner should understand the finding
  well enough to have avoided it.

## Who it is for

- Teachers and tutors reviewing a learner's program
- Learners who want feedback that explains *why*, not just *what*
- Coding assistants working in tutoring mode rather than shipping mode

## What is in the package

- `SKILL.md` — the review behaviour
- `README.md` — entry points and examples
```

### The result (what their agent delivers)

```markdown
## Summary

One correctness defect, and it is the kind that only shows up on some inputs.
Everything else in the function is fine.

## Findings

### 1. Null terminator is lost — **critical**

`reverse` writes `'\0'` over `s[len - 1]`, the last character of the
original string, and then never writes it back. The string is no longer
null-terminated, so anything that calls `strlen` or `printf("%s", s)` on it
reads past the end of the buffer.

**When it breaks:** only when the last character of the input is not
already `'\0'`. On `"abc"` it happens to work, which is exactly why it
survives testing.

**Evidence:** after `reverse("abcd")` the buffer is `"dcb\0"` — length 3, not
4 — and the original `'d'` is gone.

**Before rewriting, one question:** do you want `reverse` to return the
length, or should it return `void` and write the terminator itself? The
second is simpler to call correctly, but it constrains the caller.

## Notes on the rest

The two-pointer swap, the loop bounds, and the `int`/`size_t` mixing are all
fine here for inputs that fit in `int`. The `int len = strlen(s)` line
would be a finding in a function that accepts arbitrary-length input, and
is worth knowing about — but it is not a defect in this context.

## Next steps

- Decide the return-value convention above, then the fix is one line
- Add a test with `"a"` and with `""` — both are the cases that catch this
- Check whether any caller of `reverse` already relies on the buffer being
  terminated
```

## Extra Details

**FAQ**

**Q: Will it rewrite my code?**
A: Not unless you ask. It asks a discovery question first, then reports
findings. You decide what to change.

**Q: Is this the same as a linter?**
A: No. A linter matches patterns and cannot tell a defect from a preference.
This skill reasons about intent and impact, which is why it asks a question
before concluding.

**Q: Does it work for any language?**
A: Yes — it is language-agnostic reasoning, not a rule set.

**Q: Can I use it with my own students?**
A: Yes. It is built for tutoring mode rather than shipping mode, which is
the intended use.
