## Full Description

```markdown
## The problem

Most code judges start as a prompt: "does this submission look right?" and an
LLM answers. That verdict is unreproducible, unexplainable to the learner, and
impossible to test. It also leaks — a model that sees the hidden tests will
sometimes produce them.

## What this skill does

Installs the rule that makes a grader defensible: **the model writes
problems and hints; deterministic software decides pass or fail.** Then it
walks the rest of the design, in the order that actually matters.

- **The outcome model.** Seven categories split into two families. Learner
  failure (wrong answer, compile error, runtime error, timeout, output limit)
  and infrastructure failure (internal error) — a missing compiler reported
  as "wrong answer" teaches a learner a false lesson.
- **The test model.** Test cases as declarative data, never scripts. Two
  comparison modes, explicit visibility, and a projection step that keeps
  hidden test data off the wire.
- **The grading sequence.** Prepare → compile once → run per test → compare →
  report → clean up. Each stage records what it saw and what it aborts on.
- **Limits from configuration.** Time, memory, output size, compiler, and
  language standard are never hard-coded, and are enforced on the process
  rather than measured after the fact.
- **The trust boundary.** Submitted code is hostile input. Never invoke it as
  a shell command, never let a client choose the compiler or a path, and
  clean up the workspace on every path including timeouts.
- **Testing the grader.** One test per category, plus the properties that are
  easy to break: reproducibility, isolation, no leakage, cleanup, determinism.

## Why this beats prompting it yourself

Any model will happily tell you to "use a timeout and compare the output".
That advice misses the parts that determine whether the grader survives
contact with real submissions: the family split, the secrecy boundary, the
abort conditions, and the cleanup. This skill encodes the failure modes
you only find out about after a learner has been told their correct program
was wrong.

## Summary

Your grader needs one hard boundary and one taxonomy. Move the verdict out of
the model entirely, and split the categories so a broken machine is never
reported as a wrong answer. Below is the design.

## 1. Verdict boundary

The model may write problem statements, reference solutions, and hint text.
It may not produce test data that becomes the verdict, choose a verdict, or
soften a failure into a pass. The model should not even be importable from
the grading module — that is the check that keeps this true in six months.

## 2. Outcome model

Two families, seven categories:

| Category | Family | Learner sees |
|---|---|---|
| `passed` | learner | pass |
| `wrong_answer` | learner | which test, what it printed (public only) |
| `compilation_error` | learner | compiler diagnostics, verbatim |
| `runtime_error` | learner | exit code / signal |
| `timeout` | learner | the limit applied |
| `output_limit_exceeded` | learner | the cap applied |
| `internal_error` | **infrastructure** | nothing — logs + retry |

Attempt verdict is derived, never stored: compilation failure aborts with
`compilation_error` and zero test results; otherwise the first failing test's
category is the attempt category, with the full per-test list retained.

## 3. Data model

```python
class TestCase(BaseModel):
    id: str
    name: str
    visibility: Literal["public", "hidden"]
    stdin: str
    expected_stdout: str
    comparison_mode: Literal["exact_normalized", "whitespace_tolerant"]
    tags: list[str] = []
```

Data, not scripts: a script per test is an arbitrary-code-execution surface
in your store, and data can be linted before it is used.

## 4. Grading sequence

1. Prepare a fresh temp workspace per submission
2. Compile once — on failure, report `compilation_error` and stop
3. Run each test with the input on stdin
4. Compare with the test's mode
5. Emit the report
6. Remove the workspace in a `finally` block

## 5. Limits

Time, memory, output size, compiler path, and language standard are all
configuration. Enforce the time limit on the process, not by measuring after
the fact. Truncate output while reading, not after — a program printing 4 GB
will exhaust memory before you get to check its length. Kill the process
group, not just the child.

## 6. Trust boundary

Write the source to a fixed filename in the workspace and invoke the
compiler and binary by path. Never build a shell command string
interpolating user content. Never let the browser choose the compiler, a
path, or a test script.

## 7. Secret handling

Hidden test data leaves through exactly one path: a projection step that
builds the student-facing payload. Do not filter on the client, and do not
rely on convention.

## 8. Test plan

One test per category, plus: same submission graded twice gives the same
category; a submission that tries to read a hidden test file or write outside
the workspace fails cleanly and leaves no residue; the student-facing payload
contains no hidden test data (assert this, don't eyeball it); no workspace
survives a crashed run.

## Next steps

- Implement the projection step first — it is the one that is easy to forget
  and the one that leaks.
- Write the `internal_error` path before the happy path, so a missing
  compiler can never be reported as a wrong answer.
- Then add the category coverage tests, one per category.
```

## Extra Details

**FAQ**

**Q: Does this skill tell my agent to run submissions?**
A: No. It produces a design and a test plan. Execution is yours to implement,
and it tells you what to enforce — process-level timeouts, output caps, a
fresh workspace per submission, cleanup on every path.

**Q: Can I use it if my exercises are in a language other than C?**
A: Yes. The taxonomy, comparison modes, and sequencing are language-agnostic.
Only the compiler configuration is language-specific.

**Q: What if I already use an LLM to write my test cases?**
A: The skill covers that: a model that generates test data the verdict depends
on has influence on the verdict. Either don't, or validate the generated data
deterministically before it is used.

**Q: Why is a missing compiler not reported as a wrong answer?**
A: Because it teaches a false lesson, generates unanswerable support tickets,
and makes the pass rate measure your uptime instead of your learners.

**Q: Does it include scripts?**
A: No. It is guidance with a reference document, so it installs and runs
anywhere with no dependencies.
